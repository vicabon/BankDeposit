一、結論

可行，但不建議讓每位訪客的瀏覽器直接搜尋五家銀行官網。
最穩定的架構是：Python 負責搜尋、擷取、解析與官方資料交叉驗證；GitHub Actions 負責定時或手動執行；GitHub Pages 負責發布最新的靜態 HTML、JSON 與圖表。
高可行性GitHub Pages 顯示 HTML、CSS、JavaScript、JSON、比較表、圖表與官方連結。
中高可行性GitHub Actions 執行 Python，產生報告並自動部署。
低可行性純 GitHub Pages 在每次開啟頁面時直接爬取銀行官網，或由前端按鈕安全啟動 Python。

四、研究範圍與篩選規則

指定銀行為 LINE Bank、樂天國際銀行、將來銀行、王道銀行及匯豐銀行。每次以台灣時間判斷「今日」狀態，並優先使用銀行官方活動頁、活動辦法、公告、利率表、FAQ 及公開的官方 PDF。

  1. 限新客戶、限新戶、限新開戶或首次開戶者，不列入主要比較表。
  2. 活動尚未開始、已結束、已取消、停止受理或官方公告額滿者，不列入。
  3. 官方無法確認目前仍可承作，或只有第三方資料而無官方佐證者，不列入。
  4. 新資金不等同新客戶；若官方未限制新舊戶，可保留並明確註明新資金條件。
  5. 官方未載明的利率、額度、領息方式或資格，標示「官方資料未載明」，不得推測。

七、官方資料驗證風險

  • 銀行網頁可能使用跨來源限制、動態載入、反爬蟲或驗證碼。
  • 活動資訊可能位於 PDF，且可能是掃描影像，無法穩定自動解析。
  • 利率頁、活動頁與活動辦法可能不同步。
  • 「額度已滿」可能沒有公開公告，程式不能把未找到公告解讀成尚未額滿。
  • 登入後或 App 內才看得到的資訊，不能假設公開爬蟲可以取得。

建議狀態至少分為：可納入、已結束、已取消、已額滿、官方未明確載明、無法取得官方資料、需要人工複核。只有「可納入」才進入主要比較表。

九、建議採用方案

第一階段：Python＋GitHub Actions 每日自動搜尋與產生 latest.json、HTML、歷史快照及更新紀錄。

第二階段：GitHub Pages 以 JavaScript 讀取 JSON，提供篩選、排序、響應式表格、比較圖與官方連結。

第三階段：若確實需要訪客按鈕觸發搜尋，再增加受控的外部後端 API；不要把 GitHub Token 或銀行爬取邏輯放在公開前端。

重要限制：即使完成自動化，頁面仍應提醒使用者以銀行官方網站及實際申辦畫面為準；自動化結果代表最近一次成功檢查，不等同銀行即時承作保證。

十、更新行為的精確定義

使用者操作實際效果是否重新搜尋銀行官網
開啟 HTML讀取最近一次成功發布的資料版本否；純 GitHub Pages 無法直接執行 Python
按「重新載入資料」重新讀取已發布的 JSON／HTML否
管理者手動執行 Actions執行 Python 搜尋、校對並發布新版本是
訪客按「要求更新」呼叫受控 API，取得工作編號，等待非同步更新完成可行，但需外部後端；不保證立即完成

若採用外部 API，應顯示「排隊中、搜尋中、校對中、發布中、完成、失敗」等狀態，並設定冷卻時間或合併重複請求，避免每位訪客同時建立新的搜尋工作。

十一、資料不足與更新失敗的硬性規則

  • 只搜尋並顯示新台幣定期存款或定期儲蓄存款；外幣定存、高利活存不得混入。
  • 同一家銀行的所有符合條件方案、不同天期及不同領息選項均須保留，不得只選最高利率。
  • 無法確認既有客戶可參加、目前仍受理或必要額度狀態時，不納入主要結果。
  • 領息方式或提前解約規則未載明時，可保留其他必要條件均已確認的方案，但必須標示「官方資料未載明」。
  • 利率或天期缺漏時，不得列入利率排名，也不得以零值代替。
  • 官方來源互相矛盾且無法判定適用版本時，列為「需要人工複核」，不納入主要結果。
  • 某家銀行更新失敗時，不得把舊資料標示為「今日已確認」，也不得把抓取失敗顯示成「今日沒有符合方案」。

每家銀行應分別記錄「最近嘗試時間」、「最近成功校對時間」、「資料版本」及「結果狀態」。只有成功完成當日官方校對，才可標示為今日已確認。
